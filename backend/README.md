# Diane back-end

[PocketBase](https://pocketbase.io) (pinned version, see
`scripts/pocketbase-release.js`) extended with JS hooks.

## Prerequisites

- Linux x86_64 (dev) or arm64 (Raspberry Pi, 64-bit OS).
- Node.js >= 22 (LTS, see `.nvmrc`; `engines` requires >= 22.22.2, needed by jsdom) and npm
  (tooling only: PocketBase itself is a single binary). Use the npm bundled
  with the Node version of `.nvmrc` (npm 10.9.9, see `packageManager`):
  another npm major rewrites `package-lock.json`.

## Commands

```sh
npm ci
npm run setup     # download PocketBase into bin/, apply migrations (generates
                  # pb_data/types.d.ts), create/update the organizer account
npm run dev       # run PocketBase on http://127.0.0.1:8090 (admin UI: /_/)
npm run typegen   # regenerate app/src/lib/pocketbase-types.ts
npm test          # unit + integration tests
npm run lint
npm run typecheck
npm run format    # or format:check
```

`npm test` and `npm run typecheck` need `npm run setup` first: integration
tests run the PocketBase binary, and the hooks typecheck uses the generated
`pb_data/types.d.ts`.

Extra flags are forwarded to PocketBase: `npm run dev -- --http=0.0.0.0:8090`.

### Organizer access

No login screen (CLAUDE.md, "Accès organisateur (POC)"): the app
authenticates silently against the single account of the `organizers` auth
collection, whose password is a long random secret key. Every Diane
collection is reserved to it (`@request.auth.collectionName =
"organizers"`); anonymous requests see nothing and can change nothing.
Record requests (list, view, create, update, delete) on these collections
without a valid organizer session (no token, invalid or expired token) get
an explicit **401** (`pb_hooks/organizer-access.pb.js`), not PocketBase's
default 200 with an empty list: the app must not believe there is no data
when its session is gone (it should log in again). The public routes
(`/api/diane/r/...`, `/r/...`), the SMS gateway webhook and the auth routes
are not concerned.

```sh
cp .env.example .env            # never committed
# set DIANE_ORGANIZER_EMAIL, and DIANE_ORGANIZER_KEY to `openssl rand -hex 32`
npm run setup                   # creates or updates the account
```

`npm run setup` runs `pocketbase organizer-upsert` (a console command
defined in `pb_hooks/organizer-command.pb.js`) with these variables;
variables already set in the environment win over `.env`. Re-run it after
changing the key: the existing account is updated, never duplicated.
Running it again with the same email and key changes nothing and keeps the
app's session valid; a new key or email ends it (new token key). The
app authenticates with `POST /api/collections/organizers/auth-with-password`
(`identity` = email, `password` = key) and sends the returned token.
No e-mail flow applies to organizer accounts (password reset, verification,
e-mail change, login code by e-mail: refused by
`pb_hooks/organizer-email-flows.pb.js`, even if OTP gets enabled).

### Data model

Migrations in `pb_migrations/`, validation and defaults in `pb_hooks/*.pb.js`:

- `members`: name, email and/or phone (normalized to E.164, both unique),
  active (default true). Deleting a member deletes its invitations and
  queued SMS (right to erasure).
- `hunts`: Paris day `date` (YYYY-MM-DD, unique) and `meeting_time` (HH:MM),
  optional `max_participants` (0 = no limit), `response_deadline` before the
  hunt, `status` (default `draft`), `invitations_sent_at`,
  `reminder_sent_at`, `cancelled_at`.
- `invitations`: hunt x member (unique), `participation` (default
  `pending`), answer time and channel, the `token` of the member's answer
  link, generated by the server (43 random alphanumeric characters), and the
  outcome of the invitation per channel, `sms_status` / `email_status`:
  `sending` (claimed by a sending request, not sent yet), `sent`, `failed`
  (transport missing or in error, timeout included), `not_sent` (not
  attempted: the gateway was found unreachable earlier in the same
  sending) or `skipped` (no phone / no e-mail); same statuses for the
  reminder (`reminder_sms_status` / `reminder_email_status`) and the
  cancellation notice (`cancellation_sms_status` /
  `cancellation_email_status`), with their attempt counters
  (`reminder_sms_attempts`...).
- `message_templates`: name, body with `{date}`, `{heure}`, `{limite}`,
  `{jour}`, `{lien}` and the section `{#plusieurs}...{/plusieurs}`, kept only
  for a member with several open invitations (rendered by
  `pb_hooks/lib/message-template.cjs`), one default (seeded).
- `sms_review_queue`: SMS to check ("à vérifier"): sender number, body,
  reception time, `member` when known, `reason` (`unknown_sender`,
  `inactive_member`, `unrecognized`, `no_open_invitation`,
  `several_open_invitations`, `ambiguous`, `unknown_day`, `ambiguous_day`,
  `deadline_passed`, `hunt_closed`), `resolved` and `resolved_at` (set by
  the hook when resolved).
- `sms_inbound`: SMS webhooks already handled: gateway event id (unique),
  `member`, `outcome` (`applied`, `cancelled`, `review`, `ignored`) and
  `confirmation` (status of the confirmation SMS). No number, no message.
  Read-only for the organizer, written by the webhook only.

PocketBase's default `users` collection (open sign-up) is deleted.

### Invitations and answers

Routes (`pb_hooks/send-invitations.pb.js`, `pb_hooks/web-answers.pb.js`):

- `POST /api/diane/hunts/{id}/send-invitations` (organizer): invites every
  active member not yet invited, with the default template and the member's
  link `{DIANE_PUBLIC_URL}/r/{token}`: SMS if the member has a phone, e-mail
  if an e-mail. The hunt becomes `invitations_sent` (`invitations_sent_at`:
  first sending). Idempotent: sending again only invites new members (failed
  sends: see `resend-failed`). Without deadline, a default one is set
  (`defaultDeadline` in `pb_hooks/lib/invitations.cjs`, Paris times): the
  sending day + 2 days at 20:00 if strictly before the hunt (sent on Sunday
  morning or Sunday 23:00 -> Tuesday 20:00), else the day before the hunt
  at 20:00 if at least 2 hours ahead (user decision: time to answer), else
  none (`deadline_missing`: the organizer sets the deadline).
  Answers `{ invited, sms: { sent, failed, skipped, not_sent }, email: {...} }`;
  refusals are 409 with `data.hunt.code` = `hunt_cancelled`, `hunt_closed`,
  `deadline_passed` or `deadline_missing` (no deadline, and the day before
  the hunt at 20:00 has passed or is less than 2 hours away), 503 when `DIANE_PUBLIC_URL` is missing.
- `POST /api/diane/hunts/{id}/resend-failed` (organizer): sends again, per
  channel, the invitation SMS / e-mails that did not go out.
  - **Taken**: invitations still `pending` of active members whose channel
    is `failed` (gateway or SMTP in error, timeout, not configured),
    `not_sent` (not attempted, gateway unreachable during the sending),
    `sending` left by an interrupted request (older than the last
    PocketBase start, or than 10 minutes: `STALE_SENDING_MS`), or empty
    once the hunt's invitations were sent.
  - **Not taken**: a channel `sent`, `skipped` or being sent (recent
    `sending`); invitations already answered (or of inactive members);
    members not invited yet (nobody new is invited: see
    `send-invitations`); reminders and cancellation notices (their own
    retries, below).
  - An SMS is resent with the same gateway id (`inv-<invitation id>`): one
    that the phone took after the timeout is rejected as a duplicate
    (409) and recorded `sent`, never sent twice. Statuses are
    updated; same answer as `send-invitations`, where `invited` counts the
    invitations resent and only the resent channels are counted. Same
    refusals. Idempotent: channels to send are marked `sending` in a
    transaction (by both routes), so a second (or concurrent) call resends
    nothing already sent or being sent, and a sending interrupted by a
    restart, a power cut or a kill stays visible and is taken over; whatever
    fails again can be resent later. Each invitation is sent on its own: an
    error on one (e.g. its member deleted meanwhile) records its channels as
    `failed` and does not stop the others. A dedicated route rather
    than a parameter of `send-invitations`: a separate action in the app
    ("Renvoyer les échecs"), which never invites anybody, while
    `send-invitations` keeps its contract.
- `GET /r/{token}` (public): the members' answer page (see below).
- `GET /api/diane/r/{token}` (public): the hunt (date, time, French labels,
  cancelled), the deadline, the member's own `participation` / `answer` and
  `can_answer` (+ `refusal`). Nothing personal; unknown token: generic 404.
- `POST /api/diane/r/{token}` (public) `{ "answer": "yes" | "no" }`: records
  it (`answered_via: web`) until the deadline (or the hunt start without
  deadline); 409 with `data.answer.code` after it or for a cancelled/closed
  hunt.
- `GET /api/diane/hunts/{id}/attendance` (organizer): present, waiting list
  (invitation ids, first come first), absent, pending, free places.
- `POST /api/diane/hunts/{id}/cancel` (organizer,
  `pb_hooks/cancel-hunt.pb.js`): the hunt becomes `cancelled`
  (`cancelled_at`: first cancellation) and every invited member who did not
  answer no (pending, present, waiting list) gets an SMS and an e-mail
  « La battue du samedi 14 novembre à 8h00 est annulée. » (subject
  « Battue du samedi 14 novembre annulée »). Answers are kept. Answers
  `{ notified, sms: {...}, email: {...} }`. Idempotent, same mechanics as
  the invitations (`cancellation_*_status` claimed `sending` in a
  transaction): calling it again tells nobody twice and only resends the
  notices `failed`, `not_sent` or left `sending` by an interrupted request,
  at most 3 attempts per channel, with the same gateway id
  (`can-<invitation id>`, see Reminders). A draft is
  cancelled without notice. Later answers are refused: web 409
  `hunt_cancelled` (« La battue est annulée. »), SMS « La battue du ... est
  annulée. »; sending invitations: 409 `hunt_cancelled`.

### Members' answer page

`{DIANE_PUBLIC_URL}/r/{token}` serves `pb_public/answer/index.html`, the
same page whatever the token, with or without a trailing slash
(`pb_hooks/answer-page.pb.js`); its script
(`answer.js`, started by `main.js`) reads the token in the URL and only
calls `GET`/`POST /api/diane/r/{token}`. Not a page of the Expo app
(CLAUDE.md): plain HTML/CSS/JS, no framework, no build, no dependency, no
cookie, no browser storage, never the organizer key. For elderly members:
hunt date and time in large type, the deadline, the current answer, two
64 px buttons "Je viens" / "Je ne viens pas", a confirmation announced to
screen readers (`aria-live`, waiting list included), and plain messages for
a passed deadline, a cancelled or closed hunt, an invalid link, or an
unreachable server ("Réessayer", then the focus moves to the title of
the section shown). A member on the waiting list reads "Vous êtes sur liste
d'attente (pas encore inscrit)", never "je viens"; a cancelled hunt shows
its banner above the date, without meeting time nor answer.

- Colors copied from the app's design tokens (`app/src/theme/tokens.js`)
  into `answer.css` (`--primary` = `colors.primary.DEFAULT`,
  `--primary-foreground` = `colors.primary.foreground`...):
  `tests/unit/answer-page-files.test.ts` fails when they differ, or when
  the CSS uses another color. Update both together.
- Font: Atkinson Hyperlegible served from `pb_public/answer/fonts/` (SIL
  Open Font License, `fonts/OFL.txt`), `system-ui` as fallback. Nothing is
  loaded from another site (no Google Fonts: RGPD), checked by the same test.
- Headers of `/r/...` and `/answer/...`: `Content-Security-Policy:
default-src 'self'; base-uri 'none'; object-src 'none'; form-action
'none'; frame-ancestors 'none'` (no inline script or style),
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (also a
  `<meta name="referrer">`: the URL carries the token), `X-Frame-Options:
DENY`, `Cache-Control: no-cache` (revalidated, no personal data).
  `/api/diane/r/...` answers carry `Cache-Control: no-store`.
- PocketBase serves `backend/pb_public/` (`--publicDir`, set by
  `scripts/paths.js`; PocketBase's default is `bin/pb_public`). In
  production, keep `pb_public/` next to `pb_hooks/` and pass the same flag.
- Tests: `tests/unit/answer-page.test.ts` runs the real page in jsdom with
  a fake server (display, answers, errors);
  `tests/integration/answer-page.test.ts` checks the headers and answers
  through the page against a PocketBase instance.

Waiting list (`pb_hooks/lib/waiting-list.cjs`): a yes is `present` while
places are free (`max_participants` 0: no limit), else `waiting_list`,
ordered by `answered_at`. Answers are applied in a transaction (serialized:
never more than the maximum). Rule validated with the organizer: when a
place is freed, a new yes goes behind the members already on the waiting
list; the organizer moves someone up from the list (no automatic
promotion). A repeated yes keeps its place and time.

SMS are rendered in GSM-7 (`pb_hooks/lib/sms-encoding.cjs`): characters
outside of it are transliterated (`août` → `aout`, `ê` → `e`, `’` → `'`...),
since a single one would switch the whole SMS to UCS-2 (70 characters per
segment instead of 160). E-mails keep the accents. The default template fits
2 SMS segments for every date, tested with a 25-character and a
50-character public URL: keep `DIANE_PUBLIC_URL` at **50 characters at
most** (scheme included, e.g. `https://diane.example.org`: 25; a
Tailscale Funnel name `https://<machine>.<tailnet>.ts.net` is usually
35-45). Beyond, the SMS may take 3 segments.

### Sending: SMS gateway and e-mail

Transports (`pb_hooks/lib/transports.cjs`) are chosen by environment
variables (`.env.example`; `npm run dev` passes `backend/.env` to
PocketBase):

- SMS: [SMS Gateway for Android](https://github.com/capcom6/android-sms-gateway)
  (checked against v1.78), `POST {DIANE_SMS_GATEWAY_URL}/messages` with HTTP
  basic auth (`DIANE_SMS_GATEWAY_USERNAME` / `DIANE_SMS_GATEWAY_PASSWORD`)
  and `{ "id": ..., "textMessage": { "text": ... }, "phoneNumbers":
["+33..."] }`. `id` is deterministic per logical message:
  `inv-<invitation id>` (invitation), `rem-<invitation id>` (reminder),
  `can-<invitation id>` (cancellation notice), `cnf-<sms_inbound id>`
  (confirmation of an SMS reply). The gateway rejects an id it already
  took with 409 Conflict (local server: `MessagesService.kt`; cloud relay:
  `ErrMessageAlreadyExists`), recorded as `sent`: a message resent after a
  timeout (a slow phone may take it after the 5 s wait) is never sent
  twice, as long as the phone keeps its message history. Downside: a
  message the phone took but then failed to send (SIM error) is also seen
  as sent on a resend; check the gateway app in that case.
  Same API for the phone's local server (`http://<phone-ip>:8080`, the
  backend must reach the phone) and the cloud relay
  (`https://api.sms-gate.app/3rdparty/v1`). A 2xx (202) means queued on the
  phone, not delivered. Timeout: 5 s. Once the gateway is unreachable, the
  remaining SMS of the same request are recorded `not_sent` without trying
  (a phone switched off costs one timeout, not one per SMS). Unreachable
  means a connection error (refused, reset, DNS, no route), or a timeout
  followed by a failed quick check (`GET {DIANE_SMS_GATEWAY_URL}/health`,
  2 s, any HTTP answer counts). Go reports the same « context deadline
  exceeded » for a phone switched off (connection never established) and
  for a slow one, hence the check: when the phone answers it, the SMS that
  timed out is `failed` (it may have been taken: resending it is safe, its
  id is the same) and the next members still get theirs in the same
  sending; a slow phone then costs up to 5 s per SMS. An HTTP error answer
  (4xx/5xx) only fails its own message. Resend the failures with `resend-failed`. Just before each
  channel is sent, its `sending` status is refreshed (so `updated`), in a
  transaction checking that the invitation is still as the request left it:
  a long batch is never seen as abandoned by `resend-failed`, and a channel
  taken over meanwhile is not sent twice (`pb_hooks/shared/messaging.cjs`).
- E-mail: PocketBase's mailer with the SMTP settings of the admin UI
  (Settings > Mail settings), sender `DIANE_EMAIL_SENDER_ADDRESS` /
  `DIANE_EMAIL_SENDER_NAME` (default: the admin UI's sender). SMTP disabled:
  failed (PocketBase's `sendmail` fallback is never used).
- Not configured or in error: the invitation is created and the failure
  recorded in `sms_status` / `email_status`. Logs (PocketBase's logs, admin
  UI) carry the invitation id, the channel and a reason without personal
  data; never a phone number, an e-mail or a message.
- Tests: `DIANE_SMS_TRANSPORT=fake` / `DIANE_EMAIL_TRANSPORT=fake` write
  each message as a JSON file into `DIANE_FAKE_OUTBOX_DIR`. Never in
  production: PocketBase prints a `WARNING: DIANE_..._TRANSPORT=fake` line
  at startup (and in its logs) while one is on.

### Incoming SMS (webhook)

`POST /api/diane/sms/webhook` (public, `pb_hooks/sms-webhook.pb.js`)
receives the SMS of the gateway phone, sent by SMS Gateway for Android as
`sms:received` webhooks (format checked against docs.sms-gate.app):

```json
{
  "event": "sms:received",
  "id": "Ey6ECgOkVVFjz3CL48B8C",
  "payload": {
    "messageId": "abc123",
    "message": "OUI 14",
    "sender": "+33639985001",
    "recipient": "+33639985099",
    "simNumber": 1,
    "receivedAt": "2026-11-08T11:00:00.000+01:00"
  }
}
```

(`phoneNumber` instead of `sender` in older versions: accepted.)

**Authentication**: the app signs every request with its signing key:
`X-Signature` = hex HMAC-SHA256 of the raw body followed by the
`X-Timestamp` header (Unix seconds). The backend recomputes it with
`DIANE_SMS_WEBHOOK_SECRET`, compares in constant time
(`$security.equal`) and refuses a timestamp more than 5 minutes away
(replay). Missing or wrong signature, stale timestamp, or no secret
configured: the same `401` without detail (and nothing recorded). When
only the timestamp fails (valid signature), the backend logs « SMS
webhook refused: clock skew » with the skew in seconds (`skew_s`, nothing
else). Other events: `200 { "status": "ignored" }`.

**Gateway phone clock**: turn on automatic network date and time on the
gateway phone. The app signs each attempt with its own clock (timestamp in
seconds, recomputed on every retry, so retries are not refused); a clock
more than 5 minutes off gets every webhook refused, until the app gives up
(about 2 days of retries) and the SMS are lost. Look for « clock skew » in
the logs if replies stop arriving.

**Threat model**: the signature authenticates the gateway phone (who holds
the key), not the sender of the SMS. A spoofed sender number (possible
with some providers) is taken for the member's reply. The confirmation
SMS goes to the real member's number, so they would notice an answer they
did not send and can correct it (or tell the organizer); the organizer
also sees `answered_via: sms`. Acceptable for the POC (low stakes: a
head count).

**Handling** (answer `200 { "status": ... }`, nothing personal):

- `duplicate`: the same event id was already handled. The gateway retries
  a webhook (same id) until it gets a 2xx; it is handled once.
- `ignored`: sent from the gateway's own number (`recipient`, or
  `DIANE_SMS_GATEWAY_PHONE`): never answered.
- `review`: queued in `sms_review_queue` with its reason (member set when
  the number is known): unknown number, inactive member, message not
  recognized by `parseSmsReply` (`pb_hooks/lib/sms-reply.cjs`), no single
  open invitation for it, deadline passed or hunt closed. An invitation is
  open while the member may answer (answered or not, deadline not passed,
  hunt not cancelled, hunt not started). Without a day, the reply applies
  to the single open invitation (several → `several_open_invitations`;
  when another upcoming hunt still waits for the member's answer, its
  deadline passed → `ambiguous`: in doubt, to check, a late « OUI » for
  tomorrow must not land on next week's hunt);
  with a day (`OUI 15`), to the hunt of that day of the month (none →
  `unknown_day`, several months apart → `ambiguous_day`).
- `applied`: recorded like a web answer (same code,
  `pb_hooks/shared/answers.cjs`: waiting list, transaction,
  `answered_via: sms`), then confirmed by SMS.
- `cancelled`: the hunt is cancelled; the answer is not recorded and the
  member gets « La battue du samedi 14 novembre est annulée. ».

**Confirmation SMS** (`pb_hooks/lib/notifications.cjs`, GSM-7, a single
SMS for every date, tested), sent only to an active member whose reply was
recognized:

- « Présence OUI enregistrée pour la battue du samedi 14 novembre. Pour
  changer, renvoyez OUI 14 ou NON 14 avant le jeudi 12 novembre à 20h00. »
- « Absence enregistrée pour la battue du ... Pour changer, renvoyez ... »
- « Vous etes sur liste d'attente pour la battue du ... Pour changer,
  renvoyez ... » (accents outside GSM-7 transliterated)

Without deadline, « avant le ... » is left out. No answer
at all to an SMS to check (decision): an acknowledgement (« Message reçu,
l'organisateur va vérifier ») would cost an SMS for every spam, operator
message or unknown number, could start an exchange with an answering
machine, and tells the member nothing they can act on; the organizer sees
the queue and calls back. No loop is possible: an SMS from our own number
is ignored, a confirmation sent back to us is not a recognized reply
(queued, not answered), and a member gets at most 5 confirmations per
rolling hour (`MAX_CONFIRMATIONS_PER_HOUR`, `confirmation: skipped`
beyond).

Logs carry the event id, member id and outcome only, never a number or a
message (tested).

**Gateway setup** (SMS Gateway for Android):

1. In the app, Settings > Webhooks > Signing Key: copy the key into
   `DIANE_SMS_WEBHOOK_SECRET` (backend `.env`), restart PocketBase.
2. Register the webhook once, with the basic auth credentials of the app
   (Home tab), on the API used for sending:

   ```sh
   # local server of the phone
   curl -X POST -u "sms:$PASSWORD" -H "Content-Type: application/json" \
     -d '{"url":"https://diane.example.org/api/diane/sms/webhook","event":"sms:received"}' \
     http://192.168.1.50:8080/webhooks
   # or the cloud relay: https://api.sms-gate.app/3rdparty/v1/webhooks
   ```

   Register it on one side only (local server **or** cloud): the two keep
   separate webhook lists, each would send the SMS with its own event id
   (two confirmations).

3. The URL must be HTTPS with a valid certificate (the app refuses plain
   HTTP except to `127.0.0.1`): the public URL (Tailscale Funnel...) fits.
4. Optionally set `DIANE_SMS_GATEWAY_PHONE` to the gateway's number, in
   case the phone does not report it (`recipient` null).

### Reminders

A cron (`dianeReminders`, every 10 minutes, `pb_hooks/reminders.pb.js`)
reminds the members who have not answered, 24 hours before the response
deadline: invitations still `pending` of active members, hunts
`invitations_sent` (not cancelled or closed) with a deadline, once
(`reminder_sent_at`), and only when the invitations were sent before that
time (someone invited 15 hours before the deadline just got the
invitation). Same mechanics as the invitations (`reminder_*_status`
claimed `sending` in a transaction); until the deadline, each run sends
again the reminders `failed` or left `sending` by an interrupted run, with
limits (`noticeChannelsToSend` / `noticeRecord` in
`pb_hooks/lib/notifications.cjs`, same for cancellation notices):

- at most **3 attempts** per channel (`reminder_*_attempts`); a message
  `not_sent` (not attempted, gateway already found unreachable during the
  run) does not count;
- a **timeout** (phone off, out of the network, or slow) is `failed` and
  retried like any failure: the SMS keeps its gateway id
  (`rem-<invitation id>`), so one that the slow phone took after the 5 s
  wait is rejected as a duplicate (409) on the next attempt and recorded
  `sent`: never twice the same reminder;
- each run tries the least attempted first, in a random order otherwise:
  after a timeout the rest of a run is cut off (gateway unreachable), and
  the members cut off come first on the next run.

- SMS (GSM-7, one SMS for every date, no link to stay short; the day makes
  the reply unambiguous): « Rappel : battue du samedi 14 novembre à 8h00.
  Vous n'avez pas encore répondu. Répondez par SMS OUI 14 ou NON 14 avant
  le jeudi 12 novembre à 20h00. »
- E-mail « Rappel : battue du samedi 14 novembre », with the answer link.

### RGPD: retention of SMS data

A daily cron (`dianePurgeSmsData`, 03:17, `pb_hooks/retention.pb.js`,
durations in `pb_hooks/lib/retention.cjs`) deletes:

- `sms_review_queue` entries resolved more than **30 days** ago: enough to
  answer a member who disputes, after the hunt, how a message was handled;
- every `sms_review_queue` entry received more than **90 days** ago: an
  SMS left unresolved that long concerns a hunt long past;
- `sms_inbound` records older than **7 days** (the gateway retries a
  webhook about 2 days by default).

Deleting a member deletes their queued SMS and `sms_inbound` records.

### Rate limits

Migrations enable PocketBase's rate limiter, per client IP, with these rules
(first matching rule wins, in this order):

| Rule                            | Audience                  | Limit        |
| ------------------------------- | ------------------------- | ------------ |
| `/api/diane/r/` (answer routes) | guests                    | 20 per 10 s  |
| `*:auth` (logging in)           | guests                    | 2 per 3 s    |
| `*:create`                      | guests                    | 20 per 5 s   |
| `/api/batch`                    | guests                    | 3 per 1 s    |
| `/api/`                         | guests                    | 300 per 10 s |
| `/api/`                         | authenticated (organizer) | 600 per 10 s |

PocketBase's default rules apply to guests only: the organizer can create
many records in a row (an import, a demo data set). Logging in is always a
guest request, so `*:auth` still applies to the app's silent login: the app
should retry after a short delay on a 429. Tokens (about 256 bits) cannot be
enumerated anyway; the answer rule only slows down abuse. Guests creating
records in Diane collections get a 401 before `*:create` is counted (see
"Organizer access"). Adjust in Settings > Rate limits.

#### Deployment behind a reverse proxy (Tailscale Funnel...)

Behind a reverse proxy on the same machine (Tailscale Funnel, Caddy,
nginx), PocketBase sees every request coming from `127.0.0.1`: all members
then share a single quota (20 requests per 10 s on `/api/diane/r/`), right
after an invitation burst when many open their link. When deploying:

1. check which header the chosen proxy sets with the client IP (usually
   `X-Forwarded-For`; Tailscale Funnel: check it on a test request);
2. in Settings > Application > Trusted proxy, add that header; with
   `X-Forwarded-For`, leave "use leftmost IP" off (the rightmost IP is the
   one added by the proxy, the leftmost can be forged by the client);
3. only do it when PocketBase is reachable through the proxy only (listening
   on `127.0.0.1`): otherwise anyone can forge the header and bypass the
   limits.

### Request logs

PocketBase logs every request in `_logs` (admin UI > Logs). A migration
turns off client IPs (`logIP`: an IP is personal data) and keeps logs
**2 days** (default 5): enough to look into a problem reported the next day
or after a weekend hunt, without keeping a history of who opened their link
when. `pb_hooks/request-logs.pb.js` replaces answer tokens with `:token` in
the logged URL (`/r/{token}`, `/api/diane/r/{token}`, whatever the outcome,
429 included), and any run of 43+ alphanumeric characters (a token's
length) in the path, the query, the Referer and the User-Agent
(hand-crafted requests: upper case path, unknown route, encoded Referer).
Hook logs carry ids only (invitation, channel, reason).

### App types

`npm run typegen` applies the migrations to an empty temporary database and
generates `app/src/lib/pocketbase-types.ts` with pocketbase-typegen (never
edit it by hand). A test fails when it is out of date: run `npm run typegen`
after changing `pb_migrations/` and commit the result.

### Development databases and edited migrations

Migration `1762501100_notice_attempts.js` was changed during its review
(an `unknown` status replaced by `not_sent`) before reaching `main`. A
development `pb_data/` that applied the earlier version keeps the old
status values: start from a fresh `pb_data/` (delete it, then
`npm run setup`), or revert and reapply it
(`bin/pocketbase migrate down 1 --dir=pb_data`, then `npm run setup`).
Production and test databases are not concerned (the migration was never
deployed; tests always start from an empty database).

### First superuser

On a fresh `pb_data/`, PocketBase prints an installer URL to create the first
superuser. `npm run dev` and the integration tests never let it open a
browser (PocketBase has no option for that: `scripts/no-browser.js` puts
no-op `xdg-open`/`open` commands first in its `PATH`). Open the printed URL
yourself, or create the superuser from the command line:

```sh
bin/pocketbase superuser upsert EMAIL PASSWORD --dir=pb_data
```

## Layout

- `pb_hooks/` (`*.pb.js` hooks) and `pb_migrations/` run in PocketBase's JSVM
  (goja), **not Node**: no Node modules (`fs`, `path`...), no ESM `import`,
  no `process`/`Buffer`/`__dirname`; use the PocketBase APIs (`$app`, `$os`,
  `$http`...). Typed through `pb_data/types.d.ts`.
- `pb_hooks/lib/*.cjs` — pure business logic (SMS parsing, deadlines, waiting
  list, message templates...), shared by hooks and unit tests:
  - CommonJS (`module.exports`) using neither Node nor PocketBase APIs
    (`$app`...): data in, data out. `.cjs` because `package.json` sets
    `"type": "module"`; PocketBase only loads `*.pb.js` files as hooks.
  - Hooks load it through a path rooted at `__hooks` (the JSVM resolves other
    paths against `node_modules` or the working directory), typed by a cast:

    ```js
    const { parseSmsReply } =
      /** @type {typeof import("./lib/sms-reply.cjs")} */ (
        require(`${__hooks}/lib/sms-reply.cjs`)
      );
    ```

  - Unit tests load it with `createRequire(import.meta.url)`. Lib modules
    require each other by relative path (`require("./other.cjs")`).
  - These rules are enforced by ESLint.
- `pb_hooks/shared/*.cjs` — helpers using PocketBase's APIs shared by
  several hooks (transports and claimed sending, recording an answer),
  loaded the same way (`require(`${__hooks}/shared/messaging.cjs`)`) inside
  handlers, covered by integration tests.
- `tests/unit/`, `tests/integration/` — Vitest. Integration tests run against
  a throwaway PocketBase instance (free port, temporary data dir, test
  superuser, 127.0.0.1 exempted from rate limits) started by
  `tests/integration/pocketbase.global-setup.ts`; `rate-limit.test.ts` and
  `request-logs.test.ts` check the limits on instances without exemption; tests needing their own
  environment (transports, exact counts, process output) start one with
  `tests/integration/instance.ts`. Test instances run with
  `--automigrate=false`: changing a collection in a test never writes a
  migration into `pb_migrations/`.
- `pb_public/` — static files served by PocketBase: the members' answer
  page (browser ES modules, linted and type-checked with DOM types).
- `bin/` and `pb_data/` are git-ignored.
